We've All Fixed One Thing and Broken Another

  • Added database connections exhausted database memory
  • Auto-scaled a service triggered a cascading outage
  • Increased retries made an overloaded dependency worse
These are often locally rational decisions that interact badly with the larger system.

What Is Linear Thinking?

Linear thinking assumes a predictable chain of cause and effect: A causes B.

  • One action has one primary result.
  • More input produces roughly more output.
  • Fix the broken component and the system is fixed.

Useful for simple, isolated mechanisms.

Linear thinking is a straightforward mental model: identify a cause, predict its effect, and correct the part that failed.

What Is Non-Linear Thinking?

Non-linear thinking recognizes that cause and effect are not proportional.

Linear

A causes B. More input creates roughly more output.

Non-linear

Feedback and thresholds mean a small change can create a much larger result.

In a non-linear system, relationships between parts change the outcome. A service can be healthy at 70% utilization and behave very differently at 90%, when queues grow and retries begin.

System Anatomy: Stocks, Flows & Delays

Stocks

What accumulates?

Requests, queue messages, connections, memory, cached data.

Flows

What changes the stocks?

Requests/sec, message consumption, throughput.

Delays

How long before the system knows or reacts?

Telemetry, network, queue, deployment, human response.

Ask: what is accumulating, what is moving, and how quickly does the system respond?

The question is not whether an intervention is good. It is: what part of the system are we actually changing?

TUNE: #12 Parameters

Change a constant, threshold, or parameter.

Examples

HTTP timeout · Retry count · Thread pool · DB connection limit

More examples

Cache TTL · CPU/memory · Batch size · Rate-limit value

Example

CONTROL: #9 Delays

Change how quickly the system knows and reacts.

Batch streaming

CONTROL: #8 Balancing Feedback

Strengthen the mechanism that pushes the system toward stability.

Circuit breaker

Failure ↑ Stop calls Dependency recovers

Rate limiter

Demand ↑ Restrict inflow Protect capacity

Backpressure

Consumer slows Producer slows Queue stabilizes

Also: load shedding and fail-fast behavior.

CONTROL: #7 Reinforcing Feedback

Reduce the gain of the runaway loop.

Interventions

Exponential backoff · Jitter · Retry budgets · Request coalescing · Cache-stampede protection · Bounded concurrency

The distinction

#8: Strengthen balancing — stop when unhealthy.

#7: Weaken reinforcing — do not generate synchronized load.

Post-Incident Analysis: Climb the Ladder

  1. What happened? Event: checkout timed out.
  2. What pattern produced it? Timeouts happen during traffic spikes.
  3. What structure produced the pattern? Synchronous dependency + retries + no backpressure.
  4. What feedback loops were involved? Retry amplification + insufficient balancing.
  5. What intervention are we proposing? Parameter, buffer, feedback, information, rule, goal, or paradigm?
If every action item is configuration or retraining, we may be fixing symptoms. Ask whether the postmortem can introduce a mechanism or change the structural condition.

Architectural Takeaways

  1. Beware the Event Trap: Events are symptoms; structure generates behavior over time.
  2. Find the Loops: Ask what amplifies failure and what counteracts it.
  3. Find Stocks, Flows & Delays: What accumulates, moves, and waits?
  4. Climb the Leverage Ladder: Do not stop at parameters when the problem is structural.
  5. Question the Goal: Sometimes the highest-leverage change is changing what success means.
Good architecture does not just survive failure. It changes the dynamics that produce failure.
Close by returning to the questions: what structure created this behavior, what flow is overwhelming what stock, what loop are we creating, and how easily can we change our minds?

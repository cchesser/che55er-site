A Familiar Architecture Surprise

Every service meets its own contract.

Every dashboard looks green.

The user journey still feels broken.

The problem is often the system behavior, not one broken part.

Start with the abstract's motivation. This is the feeling we are trying to explain.

The Book Behind The Lens

Thinking in Systems

Donella Meadows gives us a simple vocabulary for complex behavior.

For architects

That vocabulary helps us reason about dependencies, queues, incentives, and surprises.

Introduce Meadows early. Keep it approachable: this is not theory for its own sake; it is language for things architects already experience.

Why This Matters In Software

Software teams are building faster, with more automation and more distributed dependencies.

A single event can cross services, queues, teams, and physical workflows.

The speed of the response does not guarantee the quality of the behavior.

Systems thinking helps us see what the architecture is accumulating.

Ground this in distributed software. The more quickly we change connected systems, the more useful pattern-level thinking becomes.

Concept first

Everything Is A System

A system is a set of parts that interact to produce behavior.

A team is a system.

A bus network is a system.

A software architecture is a system.

Keep this plain. The main move is to shift attention from parts to behavior.

The Three Things To Look For

Elements

The parts you can name.

Connections

How the parts affect each other.

Purpose

What the system is trying to do.

Meadows uses these as a starting point for understanding system behavior.

This is the basic frame for the rest of the talk.

Concept first

Events Are Easy To Notice

3:05 PM

A bus is late.

3:08 PM

Fans refresh the app.

3:12 PM

The update API slows down.

Events are vivid. That is why we organize our stories around them.

Events are exciting, urgent, and easy to narrate. They also invite a short-term response.

But Events Are Not The Behavior

One late bus is an event.

Late buses every Saturday are a pattern.

A growing delay after every demand spike is a dynamic pattern of behavior.

The pattern tells us more about the system than any single event.

Make the distinction explicit: events happen, patterns persist, and system structure generates the pattern.

Three Ways To Look At The Same System

Event

What happened?

Pattern

What keeps happening?

Structure

What relationships make it likely?

Systems thinking moves us from reaction toward explanation.

This is the central teaching frame for the first half.

Linear Thinking Tells A Clean Story

Bus is late
Fans are upset
Add more buses

A causes B, so fix A.

Linear thinking is useful for simple mechanisms. The trouble starts when the response changes the conditions that created the event.

Non-Linear Systems Answer Back

Add capacity
More people choose the route
The bottleneck moves

Small changes can have large effects. Large changes can have almost none.

Cause and effect are not always proportional.

Introduce non-linearity as response that changes with conditions, thresholds, capacity, and feedback.

Accumulation Changes The Shape Of The Problem

A stock is something that can build up or drain down. A flow changes it.

Arrivals
People waiting
Boardings

When arrivals briefly exceed boardings, the queue grows.

When the queue grows, the next event happens in a different system.

Stocks are memory. The system carries yesterday's imbalance into today's experience.

Look At Behavior Over Time

Event view

Why was this bus late?

Who should respond?

Pattern view

Why does delay grow after 3 PM?

What repeats each match day?

Plot the behavior before explaining the event.

This is where simple time-series sketches or your illustration can do a lot of work later.

Delays Hide The Real Cause

An action can change the system now, while its consequences appear later.

  • A capacity change affects demand after people notice it.
  • A queue grows before a dashboard shows the trend.
  • A notification changes arrival behavior after it is sent.

By the time the effect arrives, we may be responding to a different event.

Delay is the bridge between linear stories and non-linear behavior.

Feedback Makes Behavior Circular

A system's output can become an input.

Reinforcing

Change feeds more change.

Balancing

Change activates a constraint or correction.

This is where a simple cause-and-effect story starts to bend.

Define feedback before the case study. The MatchBus loops later should feel like applications of this vocabulary.

Purpose Changes What Counts As Success

Local success

More requests accepted. Faster response time. Higher throughput.

System success

The promised journey works for the people using it.

The metric is part of the system because it changes what people optimize.

This sets up the later human/process scan. Metrics are information and incentives at once.

Our Case Study: MatchBus KC

MatchBus KC is a software system that helps move World Cup fans by bus to Kansas City's Arrowhead stadium.

Fans
Transit App
Bus Fleet
Stadium Gates
Operations Center

We will start with the technical dependency design, then scan out to the larger busing system.

Introduce the case only now. The business workflow is simple; the architecture and its behavior are the focus.

Two Systems At Once

Software system

Reservations, trip updates, bus telemetry, capacity estimates, alerts, and operator tools.

System around it

Fans, pickup lots, buses, roads, drivers, gates, staff, weather, and time.

The software is inside the busing system, not above it.

This is the boundary move. We start technically, then widen the boundary when the behavior demands it.

Apply the lens

MatchBus Stocks

Fans waiting

People at pickup lots, on buses, and at gates.

Buses available

Buses ready, loading, driving, delayed, or returning.

Update requests

People asking the software, "Where is my bus?"

The important new stock is update requests, because it sets up the software overload failure.

MatchBus Flows

Fan flow

Arrive, board, ride, unload, enter.

Bus flow

Stage, load, drive, unload, return.

Data flow

Telemetry, estimates, alerts, updates.

Backlog appears when inflow is higher than outflow for long enough.

Make the concept concrete and approachable.

Queues Are Stocks In Both Systems

Physical queue

Fans waiting to board a bus.

Software queue

Trip update requests waiting to be handled.

Different materials, same systems idea.

This reinforces "everything is a system" without heavy language.

Apply the lens

MatchBus Delays

A delay is the time between a change and when the system reacts to it.

  • Traffic slows a bus before the estimate changes.
  • A dashboard updates after the queue has already grown.
  • Fans react after a notification is sent.
Delays are one of the big reasons systems surprise us.

Delayed Truth In Software

Bus delay starts at 3:10
Telemetry catches up at 3:18
Fans still see old ETA

A fast answer can still be the wrong answer for the moment.

Keep the language simple. This is stale data and eventual consistency in systems-thinking language.

The Dangerous Question

"Is the dependency healthy?"

A better question is:

"Is this answer fresh enough for the promise we are making?"

This makes the delay concept useful for architecture reviews.

Apply the lens

MatchBus Feedback Loops

A feedback loop happens when an action changes the system, and that change affects the next action.

Reinforcing

More creates more.

Balancing

The system pushes back toward stability.

Define both types before applying them.

Reinforcing Loop: Demand Surge

App says "leave now"
More fans arrive together
Boarding delay grows

The app can create the peak it is trying to manage.

Use this as an easy, human example of a reinforcing loop.

Software Failure: Where Is My Bus?

  1. A few buses fall behind.
  2. Fans refresh the app for updates.
  3. The update API and worker queue get overloaded.
  4. Updates get slower and older.
  5. More fans refresh because they do not trust the app.

The software system becomes part of the delay.

This is the explicit software failure the user requested. Tie it to real distributed systems: overload, retries, polling, stale reads.

The Overload Loop

Update delay grows
Fans refresh more
Request queue grows
Updates get older
Workers fall behind
Request queue grows

This is a reinforcing loop: more delay creates more load, which creates more delay.

This should be memorable for software engineers.

A Balancing Loop

Boarding queue rises
App recommends later windows
Arrival rate smooths out

Balancing loops are how systems regain control.

Keep this optimistic and practical.

Software Balancing Moves

Protect

Rate limit refreshes and collapse duplicate requests.

Tell the truth

Show "last updated" and confidence, not just an ETA.

Push updates

Notify fans when status changes instead of making them poll.

These are architectural controls tied to the feedback-loop concept.

Apply the lens

MatchBus Boundaries

A boundary is what you decide to include when you explain the system.

Small boundary: the update API.

Bigger boundary: the app, fans, buses, gates, staff, and decisions they make.

Different boundary, different architecture problem.

This is a simple and important systems-thinking move.

Green Services, Bad Journey

Small boundary

  • Reservation API: green
  • Notifications: green
  • Maps integration: green

Bigger boundary

  • Fans are confused
  • Buses are late
  • App updates are stale
This directly supports the abstract's distributed-systems surprise.

People Are Part Of The System

App status is unclear
Staff manually redirect fans
Boarding slows down

Manual work is not outside the architecture if the system depends on it.

Keep this respectful. Human work is a real dependency.

Apply the lens

MatchBus Leverage Points

A leverage point is a place where a change can shift system behavior.

Low leverage

Make one part faster.

Medium leverage

Change a feedback path or rule.

High leverage

Change what the system optimizes for.

Keep Meadows' leverage points accessible. Avoid the full ladder unless asked.

Leverage In MatchBus KC

Numbers

Add API capacity or more workers.

Feedback

Feed queue depth, bus delay, and gate speed back into recommendations.

Goal

Optimize for fans inside before kickoff, not just app response time.

This applies leverage points to both software and the larger busing system.

Architecture Changes That Matter

  • Make trip windows capacity-aware before fans commit.
  • Show freshness and confidence for every estimate.
  • Use push updates to reduce refresh storms.
  • Give operators one place to update app, signs, and staff scripts.
  • Measure the full journey, not just service uptime.
These should feel concrete and reusable.

The Pattern To Practice

  1. Start with the recurring pattern, not the loudest event.
  2. Describe the elements, connections, and purpose.
  3. Mark stocks, flows, delays, and non-linear thresholds.
  4. Look for reinforcing and balancing feedback loops.
  5. Scan out to human and process dependencies.
  6. Choose leverage points that improve the whole behavior.
This is the takeaway method: move from event, to pattern, to structure, then choose an intervention.
